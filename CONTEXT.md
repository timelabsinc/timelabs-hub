# Labs OS — System Context

> Self-contained brief on **Labs OS**, the self-hosted business OS for Timelabs Co, running at `ops.timelabsco.in`.
> Paste this into a new Claude/agent session — on this machine or another one — to onboard it instantly.
> Canonical copy lives in the repo at `CONTEXT.md` (pulled via `git clone`/`git pull`); a standalone copy sits at `/root/labs-os-context.md` on the primary server. Keep both in sync when either changes materially.
> Last updated 2026-07-22.

## What it is (the vision)
Labs OS is **not a website builder** — it's a **full autonomous AI assistant for the business** (Timelabs Co, an India-based Shopify DTC brand selling Seiko watch-mod parts and complete builds; store `xd2fwj-1h.myshopify.com`). The end goal: it **automates, schedules, and does everything that currently takes manual effort**. It runs entirely on one VPS; the browser is the only client. Brand family (Google-style): **Labs Home** (dashboard), **Labs Drop** (files), **Labs Ledger** (costs), **Labs Chat** (agent), **Labs Tools** (launcher). Umbrella = "Labs OS". Company is still "Timelabs Co". **Not wanted: logo/image generation.**

## Working on this from another machine
If you're a fresh Claude Code session (or a developer) on a **second machine**, building more tools for Labs OS:
- You have **root SSH** to the primary server: `ssh root@ops.timelabsco.in` (key-only auth; ask the owner to authorize your public key if you don't have access yet — see "Access & security" below).
- The live code is at `/root/ops-dashboard/` **on the primary server** — that's where you develop and where the generators actually run (they write to `/var/www/ops/*.html`). Either SSH in and edit there directly, or clone the repo locally, make changes, push, then `git pull` on the server and re-run the affected generator.
- **Repo:** `github.com/timelabsinc/timelabs-hub` (private; `timelabsinc` is a USER account, not an org — use the `/user/repos` API if scripting against it). Secrets (`.env`, `.shopify-oauth.json`) are gitignored — you will need the owner to hand you `.env` values separately if your work touches Shopify; don't try to regenerate them yourself.
- **Follow the generator pattern religiously** (see Architecture below) — it's the one rule that keeps this whole system coherent. A new tool = a new `<name>.py` generator that imports from `hub_shell.py` and writes to `/var/www/ops/<name>.html`, registered in `tools.py`'s `TOOLS` list and in `generate.py`'s refresh loop.
- **Validate before you consider anything done:** `python3 -c "import ast; ast.parse(open('yourfile.py').read())"` for syntax, then actually run the generator and `node --check` the emitted `<script>` blocks (extract them with a small regex — see any recent commit for the pattern). This project has caught real bugs this way every session.
- **Keep the shared chrome uniform.** Every generated page must carry `hub_header`/`hub_footer` from `hub_shell.py` so brand, nav, and the "Ask Labs" assistant stay consistent. Don't hand-roll a header.

## Architecture
- **nginx** (:443 TLS, Let's Encrypt) is the only public web surface. Routes: `/ops/` static+SSO; `/ops/agent/api/` → :8901 (sets `X-User-Email`); `/drop/` SPA + `/drop/api/` → :8903 (sets X-User-Email); `/s/` → :8903 **public, no auth** (Drop share links, token-gated).
- **Generator pattern (the core rule):** pages are server-rendered by Python and **never hand-edited** — `/var/www/ops/*.html` and `/var/www/drop/index.html` are build output, always regenerate from source. `hub_shell.py` is the shared shell/design system: `HUB_STYLE` (CSS, includes the assistant + rich-text-editor styles), `HUB_SCRIPT`/`WHOAMI_JS` (JS, includes the "Ask Labs" assistant — `ASSIST_JS`/`ASSIST_CSS`), `hub_header`/`hub_footer`, `page()`, `RTE_JS`/`RTE_CSS` (shared rich-text editor, `window.LabsRTE`). Each tool is a generator reusing the shell: `generate.py`→index.html (Home), `ledger.py`, `tools.py`, `blog.py`, `product_updater.py`, `product_builder.py`, `content_updater.py`, `theme_editor.py`, `files.py`. `generate.py` `main()` rebuilds Home + all tool generators in one pass — this is the daily-refresh loop; **add any new generator to its module list** or it goes stale silently.
- **Two Python envs (gotcha):** `ops-agent-chat.service` (:8901) runs on **system python3** (no openpyxl/pillow) → shells out to venv for those. Generators + `drop_server.py` run on **venv** (`/root/ops-dashboard/venv/bin/python`). `shopify_api.py` is stdlib-only (urllib only) so system python can import it directly.
- Design language = "Meridian": light-first + dark (both themed, `prefers-color-scheme` + explicit toggle), system sans, gold accent `#996c1f`/`#d8a94c`. Owner's taste: clean modern SaaS, no themed decoration/gauges/gimmicks.

## The agent (Hermes / Claude) — "Labs Chat" + "Ask Labs"
- `run_hermes(prompt, model, provider)` shells to the `hermes` CLI. Model aliases: `claude`=claude-sonnet-4-6/anthropic (also used directly for vision + structured-JSON tasks like theme/product drafting), `free`, `minimax`.
- Chat backend (`agent_chat_server.py`): `POST /send` (single-flight `LOCK`; soft-wait then `{pending}` + poll `/history` — reused by both the full Chat UI and the omnipresent widget), `/session/new`, `/history`, `/whoami`, `/events`.
- **`memory_facts` table** (hermes.db) = the agent's knowledge base; category `labs_os` holds the facts about this OS itself (~15 as of this writing) — the agent's PREAMBLE points it there. **`hub_events` table** = the cross-app activity bus ("what's new"): kinds include product_create/update/media, bulk_content, page_update, theme_update/revert, share_created/revoked, gdrive_export/import, invoice_import, member_add/remove, shopify_connected.
- **"Ask Labs"** — an omnipresent assistant (floating button + Ctrl/Cmd-K) injected into every generated page via `hub_shell.py`, reusing the exact same `/send`+poll backend so it can both answer questions and act through the agent's tools. Context-aware suggestion chips per page.

## Shopify integration
- `.env`: `SHOPIFY_SHOP` + `SHOPIFY_ADMIN_TOKEN` (shpat_, chmod 600) via OAuth app "timelabs-blog-forge". **Scopes (widened + reconnected 2026-07-21, full commerce set, confirmed live):** read/write products, content, online_store_pages, online_store_navigation, **themes**, **read_orders**, read/write **inventory**, read_customers.
- **Gotcha:** changing the app's configured scopes does NOT upgrade an already-issued token — you must re-run `/ops/agent/api/shopify/connect` to mint a fresh one, AND the connect flow only requests whatever's in the `SHOPIFY_SCOPES` constant in `agent_chat_server.py`, so widen that constant first if you're adding a new scope.
- `shopify_api.py` = the shared access layer everything imports: Admin **GraphQL** 2024-10 (products/pages/themes) + REST **Asset API** (`_admin_rest`, for reading/writing `settings_data.json` — themes have no GraphQL mutation for settings). All Shopify HTTP endpoints live under `/ops/agent/api/shopify/*` in `agent_chat_server.py`, admin-gated by `X-User-Email`.

## Tools (all live as of 2026-07-22 — nothing left "in progress")
- **Home** (`/ops/#overview`) — dashboard. Sales still come from a `metrics_snapshot` bridge, not a live Shopify pull; `read_orders` is now granted so wiring it live is a pending follow-up, not a scope blocker anymore.
- **Drop** (`/drop/`) — the product-media store, kept **purely functional**, deliberately separate from the System files browser. Chunked resumable uploads, thumbnails, Organize/OCR clustering, Google Drive **import** (working) and **export** (2026-07-21: upload a file or sync a whole folder to Drive — needs the owner to reconnect Drive once for write scope, `drive.file`, alongside the original `drive.readonly`; the Drive sheet has an in-app "Reconnect" button). **Sharing:** full download links (`/s/<token>`, revocable) AND a separate **view-only "customer" mode** (`mode:view`) — thumbnail only, `/raw` blocked (403), no download button, right-click/long-press/drag-to-save blocked client-side, folder shares render as an in-page shielded lightbox grid rather than linking bare image URLs. (Honest limit: this deters casual saving, not screenshots.) **Get info** modal (size, kind, image dimensions, dates, share links) via `/drop/api/info`.
- **Ledger** (`/ops/ledger.html`) — supplier invoices → suppliers.db; review-gated import (preview then `commit:true`), shells to venv python for openpyxl.
- **Quick product updater** (`/ops/product-updater.html`) — edit existing products: inline price/status (debounced autosave) + a deep editor (title/type/tags/images) whose description field is the shared **rich-text editor** (`LabsRTE`), not a raw-HTML textarea.
- **Product builder** (`/ops/product-builder.html`) — create new products from title/type/price/tags/description + photos (pick from Drop — auto-shares each photo to get a public `/raw` URL Shopify can fetch — or paste URLs). **"Draft the details with AI"**: sends the photos to Claude vision, which writes title/type/tags/brand-voice description/suggested price, pre-filling the form for review (`POST /shopify/product/ai-draft`). Description field is also `LabsRTE`.
- **Content updater** (`/ops/content-updater.html`) — bulk product-copy ops: insert/update an idempotent named block (marked with `<!--labs:slug-->…<!--/labs:slug-->` so re-running updates in place instead of duplicating) or find/replace across many products, with a dry-run diff preview before any write; plus a store-**Pages** editor (About, policies, etc.) via `read/write_online_store_pages`.
- **Theme editor** (`/ops/theme-editor.html`) — **prompt-driven**: describe a look in plain language → the request + the live theme's real `settings_data.json` (228 editable settings: 53 scalar + 175 colours across 5 schemes) go to Claude → it returns a validated JSON patch (existing keys only, type-coerced) → UI shows a diff with colour swatches and per-change checkboxes → owner approves → write. Every apply snapshots the prior `settings_data.json` to `theme-backups/` for one-click **Undo**. Endpoints `/shopify/theme/{settings,suggest,apply,revert}`.
- **Blog builder** (`/ops/blog.html`) — 27 queued topics → SEO drafts for the store (publish still needs a token in Blog Studio's config.json — open item).
- **System files** (`/ops/files.html`, admin-only) — a clean, read-only, traditional file browser over the Hermes home (`/root`) — navigate, hidden-file toggle, inline text preview, download. Backend `/ops/agent/api/fs/{list,read,download}`, confined to `/root` via realpath (blocks `..`/symlink escape). **Credential files are listed but their contents withheld** (`.env`, keys, anything with secret/oauth/token/password/apikey in the name) — deliberately conservative. This is explicitly **not** Drop; Drop is product media, this is the system view.
- **Order form** (`/ops/order-form.html`, added 2026-07-22) — log an order in seconds; open to any SSO user, not admin-only. Four tabs: New order / Orders / Customers / What's selling.
  - **Paste-to-fill** is the whole point: staff paste a labelled block (`Name:/Email:/Phone no:/Address:/Pincode:`) and the fields split themselves — multi-line addresses join, unlabelled blocks fall back to regex for email/phone/pincode. Parser is JS in `order_form.py` (`parseBlock`); a **Paste from clipboard** button covers phones where there's no ⌘V.
  - **Photos**: ⌘V paste event, an explicit clipboard-API button, drag-drop, or the file picker (camera roll on iOS) → uploaded via the existing `/upload`, pushed to the Drive folder "Labs OS Order Photos", links stored on the row (`photo_links` JSON, `drive_link` = first).
  - **Structure derived server-side** via `POST /orders/parse`, so the vocabulary has one home: `india_places.py` turns the address into city/state (state list + city list + "segment before the state" fallback, no pincode dataset), and `order_taxonomy.py` keyword-matches the product text into case style / dial colour / dial style / case colour / movement / size. Case-style vocabulary is seeded from the store's real `productType` values, cached in `.taxonomy-cache.json`, refreshed with `python3 order_taxonomy.py --refresh`. Colour matching is **anchored** — "rose gold blue dial" gives blue dial + rose gold case — which is the part to be careful not to regress.
  - **Customers** (`customers.py`, `customers` table) roll up from orders keyed on phone→email→name: counts, spend, AOV, first/last order, first source, and auto tags (`repeat` ≥2 orders, `VIP` ≥5 orders or ₹50k). Totals are **recomputed from `orders` each save**, never incremented, so edits/deletes can't drift them.
  - **Sheet mirror** has two tabs — Orders (append) and Customers (upsert by id in column A). `orders_resync.py` rebuilds both tabs from the DB (`--backfill` fills columns on old rows, `--sheets` re-pushes); it only ever writes sheet-from-DB.
  - Endpoints: `POST /orders/{create,parse}`, `GET /orders/{list,meta}`, `GET /customers/list`. Inputs are **16px** — anything smaller makes iOS Safari zoom on focus and not zoom back.

## Google (Drive + Sheets)
`google_api.py` is the shared access layer for both — stdlib `urllib` only (no `gspread`), so system python can import it. Client at `/root/oauth-client.json`, token at `.gdrive-token.json`, IDs cached in `.orders-sheet.json` (all gitignored).
- **Live token holds only `drive.file` + `drive.readonly` — and that is sufficient for Sheets**, because `drive.file` covers any file the app itself created and Labs OS created the Orders spreadsheet. Enabling the Sheets API in the Google Cloud project was the only thing needed; **no reconnect was required.**
- `/gdrive/connect` now also requests `spreadsheets`, which only matters if you ever want to write to a spreadsheet a human created by hand — `drive.file` cannot touch those. That wider scope applies automatically the next time Google is reconnected for any reason.


## Driving it from a terminal (and how Hermes acts)
`labs` (/usr/local/bin/labs -> bin/labs) exposes the whole system to the shell and therefore to the agent. It imports the same shopify_api.py / google_api.py the web tools use, so it reuses the credentials already in .env — never issue new Shopify/Google keys.
- Reads: `labs orders` (live storefront + logged, merged), `products`, `product <id>`, `pages`, `page <id>`, `blogs`, `articles`, `article <id>`, `theme [--filter]`, `costs`, `drive`, `search "green dial"` (Drop photos by content), `files`, `customers`, `events`, `access`, `topics`.
- Writes: `product-create/update`, `page-update`, `article-create/update`, `theme-set key=value`. **Every write is a dry run that prints the plan until you add `--execute`**, and executed writes log to `hub_events`.
- **Agent toolset is role-aware**: admins get `terminal` (so the agent can actually run `labs`), everyone else keeps the safe web-only set. `/send` is reachable by any signed-in user, so a blanket grant would let a restricted role run root commands; admins already hold root SSH so it adds no privilege for them. See `toolset_for()` in agent_chat_server.py.
- `memory_facts` now also carries categories **`preference`** (how the owner wants work done, the writing voice, design taste, what is ruled out, safety rules) and **`business`** (price bands, landed cost, banking overhead, order channels). Read those before writing copy or building UI.

## Tool access (roles)
`access_store.py` + `/ops/access.html`. Roles: admin / full / orders / **intake** (order form only). Enforcement is layered — a generated nginx map (`/etc/nginx/conf.d/labs-access.conf`) bounces a restricted role off `/ops/` to its own landing page so the HTML is never served; `sync_nginx()` runs `nginx -t` and reverts on failure. Intake lands on `/intake/`, a nav-stripped copy of the order form.
