# Labs OS — System Context

> Self-contained brief on **Labs OS**, the self-hosted business OS for Timelabs Co, running at `ops.timelabsco.in`.
> Paste this into a new Claude/agent session — on this machine or another one — to onboard it instantly.
> Canonical copy lives in the repo at `CONTEXT.md` (pulled via `git clone`/`git pull`); a standalone copy sits at `/root/labs-os-context.md` on the primary server. Keep both in sync when either changes materially.
> Last updated 2026-07-31.

## What it is (the vision)
Labs OS is **not a website builder** — it is the private operating system and AI control plane for Timelabs Co (an India-based Shopify DTC brand selling Seiko watch-mod parts and complete builds; store `xd2fwj-1h.myshopify.com`). The browser is the main client and the production stack runs on one VPS. Brand family: **Labs Home** (operating dashboard), **Labs Drop** (product media), **Labs Ledger** (costs), **Labs Command** (Hermes conversations and control), **Labs Orders/Supplier**, and **Labs Tools** (launcher). Umbrella = "Labs OS"; the company remains "Timelabs Co". The long-term goal is safe automation with explicit review boundaries, not unreviewed autonomy. **Not wanted: logo/image generation.**

## Working on this from another machine
If you're a fresh Claude Code session (or a developer) on a **second machine**, building more tools for Labs OS:
- You have **root SSH** to the primary server: `ssh root@ops.timelabsco.in` (key-only auth; ask the owner to authorize your public key if you don't have access yet — see "Access & security" below).
- The live code is at `/root/ops-dashboard/` **on the primary server** — that's where you develop and where the generators actually run (they write to `/var/www/ops/*.html`). Either SSH in and edit there directly, or clone the repo locally, make changes, push, then `git pull` on the server and re-run the affected generator.
- **Repo:** `github.com/timelabsinc/timelabs-hub` (private; `timelabsinc` is a USER account, not an org — use the `/user/repos` API if scripting against it). Secrets (`.env`, `.shopify-oauth.json`) are gitignored — you will need the owner to hand you `.env` values separately if your work touches Shopify; don't try to regenerate them yourself.
- **Follow the generator pattern religiously** (see Architecture below) — it's the one rule that keeps this whole system coherent. A new tool = a new `<name>.py` generator that imports from `hub_shell.py` and writes to `/var/www/ops/<name>.html`, registered in `tools.py`'s `TOOLS` list and in `generate.py`'s refresh loop.
- **Validate before you consider anything done:** `python3 -c "import ast; ast.parse(open('yourfile.py').read())"` for syntax, then actually run the generator and `node --check` the emitted `<script>` blocks (extract them with a small regex — see any recent commit for the pattern). This project has caught real bugs this way every session.
- **Keep the shared chrome uniform.** Every standard generated page must carry `hub_header`/`hub_footer` from `hub_shell.py` so brand, nav, and the “Ask Labs” entry to Command stay consistent. Command itself deliberately owns the entire viewport and does not render the standard footer.

## Architecture
- **nginx** (:443 TLS, Let's Encrypt) is the only public web surface. Private routes (`/ops/`, `/intake/`, `/drop/`, `/drop/api/`, `/drop/files/`, and `/ops/agent/api/`) validate both the Google session and the role. `/s/` is intentionally public and token-gated for Drop shares. nginx sends the authenticated email to the two loopback-only Python services; clients cannot assert their own trusted identity through the public vhost. The combined page gate receives nginx's raw request URI, percent-decodes it exactly once and rejects malformed, backslash, NUL and `.`/`..` paths before authorizing a canonical namespace; keep traversal probes in the deploy gate.
- **Generator pattern (the core rule):** pages are server-rendered by Python and **never hand-edited** — `/var/www/ops/*.html` and `/var/www/drop/index.html` are build output, always regenerate from source. `hub_shell.py` is the shared shell/design system: `HUB_STYLE`, `HUB_SCRIPT`/`WHOAMI_JS`, `hub_header`/`hub_footer`, `page()`, and the rich-text editor (`window.LabsRTE`). Each tool is a generator registered in both `tools.py` and `generate.py`; `generate.py` rebuilds the complete surface. Drop’s source UI is `www/drop-index.html`. Command is generated by `command.py` but intentionally uses its own full-viewport application shell.
- **Two Python envs (gotcha):** `ops-agent-chat.service` (:8901) runs on **system python3** (no openpyxl/pillow) → shells out to venv for those. Generators + `drop_server.py` run on **venv** (`/root/ops-dashboard/venv/bin/python`). `shopify_api.py` is stdlib-only (urllib only) so system python can import it directly.
- Design language = "Meridian": light-first + dark (both themed, `prefers-color-scheme` + explicit toggle), system sans, gold accent `#996c1f`/`#d8a94c`. Owner's taste: clean modern SaaS, no themed decoration/gauges/gimmicks.

## The agent (Hermes / Claude) — Labs Command
- `run_hermes(prompt, model, provider)` shells to the `hermes` CLI. Model aliases: `claude`=claude-sonnet-4-6/anthropic (also used directly for vision + structured-JSON tasks like theme/product drafting), `free`, `minimax`.
- Command (`/ops/command.html`) replaces the old Chat page. It is a responsive three-pane controller on desktop and a single-pane app with conversations/context drawers and bottom navigation on phones. A conversation is private to its creator by default; admins can inspect all. Selection is persisted in the URL and guarded local storage, and overlapping loads cannot overwrite a newer selection.
- Chat backend (`agent_chat_server.py`): `POST /send` (single-flight `LOCK`; soft wait then `{pending}` + poll `/history`), `/session/new`, `/sessions`, `/history`, `/whoami`, and `/events`. The shared “Ask Labs” entry opens the current Command session instead of maintaining a second competing chat surface.
- **`memory_facts` table** (hermes.db) = the agent's knowledge base; category `labs_os` holds the facts about this OS itself (~15 as of this writing) — the agent's PREAMBLE points it there. **`hub_events` table** = the cross-app activity bus ("what's new"): kinds include product_create/update/media, bulk_content, page_update, theme_update/revert, share_created/revoked, gdrive_export/import, invoice_import, member_add/remove, shopify_connected.
- Agent capabilities are authorization-aware. Only the two hardcoded admins receive Hermes `terminal`; other roles receive a restricted `web,clarify,vision` toolset with Hermes rules ignored and a prompt that does not claim owner/terminal access. Any AI job fed untrusted external text (Reddit, Drop OCR, weekly brief, generator summaries) is similarly run without terminal. This separation is a security boundary, not a UI preference.
- Command is not yet a durable automation engine. Long calls can finish in the conversation, but there is no persisted run queue with pause/cancel/retry/idempotency, typed approvals, or automatic recovery across service restarts. Build that substrate before enabling unattended writes.

## Shopify integration
- `.env`: `SHOPIFY_SHOP` + `SHOPIFY_ADMIN_TOKEN` (shpat_, chmod 600) via OAuth app "timelabs-blog-forge". `shopify_scopes.py` is the reviewed least-privilege contract: read/write products, content, online-store pages/navigation, themes and inventory; read customers/orders; plus `read_all_orders` so refunds/edits older than Shopify's default 60-day window still reconcile. The live token currently has 166 additional grants from an over-broad app configuration; `healthcheck.py` reports that until the owner narrows the app and explicitly reconnects.
- **Gotcha:** changing the app's configured scopes does NOT upgrade an already-issued token — you must re-run `/ops/agent/api/shopify/connect` to mint a fresh one, and the connect flow requests the contract in `shopify_scopes.py`. Review that contract first if a feature genuinely needs another scope.
- `shopify_api.py` = the shared access layer everything imports: Admin **GraphQL** 2026-07 (products/pages/themes/orders) + REST **Asset API** (`_admin_rest`, for reading/writing `settings_data.json` — themes have no GraphQL mutation for settings). All Shopify HTTP endpoints live under `/ops/agent/api/shopify/*` in `agent_chat_server.py`, admin-gated by `X-User-Email`.
- OAuth connect/callback is admin-only and binds a one-time, short-lived state to the actor and configured `.myshopify.com` shop using a secure SameSite cookie. The callback verifies state, shop, HMAC and required scopes before atomically replacing the token. Product/content/theme writes remain review-gated; Shopify/store writes require an explicit owner-approved apply.
- `shopify_order_sync.py` reconciles by Shopify `updatedAt` with an overlap window, not only by creation time. It paginates both orders and line items; refreshes current/refunded money, financial state, products and contact/address fields; and recounts both old and new customer identities. Sheet rows are indexed once and written together with explicit destinations in one idempotent `RAW` batch; a cross-process file lock serializes the key scan/write with agent and resync mutations. Quota/credential failures persist as a health failure and keep the atomic Shopify watermark behind so the next timer retries the mirror. A local contact correction sets an override fingerprint so an unchanged Shopify snapshot cannot erase it; matching Shopify to the correction clears the override, while a new conflict produces a non-PII staff activity alert. Anonymous/redacted Shopify orders never collapse into one fake customer. Once an order is committed to a supplier, imported updates preserve the local build specification, quantity, stage and supplier visibility and emit one deduplicated `shopify_conflict` per material remote revision (build, cancellation, financial state or amount).

## Tools
- **Home** (`/ops/`) — dashboard sourced from the local unified order log. All sales views share `order_metrics.py`: cancelled, refunded/voided and stock builds are operational records, not revenue. Expensive aggregates are bounded and recent orders are separately limited.
- **Drop** (`/drop/`) — product-media storage, deliberately separate from System files. It supports chunked resumable upload, search/OCR, Drive import/export, ZIP download, order-photo picking, private role-checked files, and revocable public share tokens. Upload and background-job IDs are random and owner-bound; operations have concurrency, size, file-count, disk-reserve and 24-hour expiry limits with atomic metadata/cleanup. Gallery thumbnails use a two-worker generation pool plus per-key deduplication; the systemd cgroup starts throttling at 1 GiB and contains the service at 2 GiB/512 MiB swap with automatic restart on failure. Order and Reddit media are copied out of temporary uploads into permanent, private local storage. Customer “view-only” mode deters ordinary saving but cannot prevent screenshots.
- **Ledger** (`/ops/ledger.html`) — supplier invoices → `suppliers.db`. Preview creates a short-lived, actor-bound frozen manifest; commit must present the same token/selection. Imports are serialized across processes and database bookkeeping failures fail closed.
- **Quick product updater** (`/ops/product-updater.html`) — edit existing products: inline price/status (debounced autosave) + a deep editor (title/type/tags/images) whose description field is the shared **rich-text editor** (`LabsRTE`), not a raw-HTML textarea.
- **Product builder** (`/ops/product-builder.html`) — create new products from title/type/price/tags/description + photos (pick from Drop — auto-shares each photo to get a public `/raw` URL Shopify can fetch — or paste URLs). **"Draft the details with AI"**: sends the photos to Claude vision, which writes title/type/tags/brand-voice description/suggested price, pre-filling the form for review (`POST /shopify/product/ai-draft`). Description field is also `LabsRTE`.
- **Content updater** (`/ops/content-updater.html`) — bulk product-copy ops plus store Pages. A preview freezes the actor, exact product selection and proposed bodies in a short-lived token; apply verifies the token and confirms descriptions have not drifted before the first write.
- **Theme editor** (`/ops/theme-editor.html`) — **prompt-driven**: describe a look in plain language → the request + the live theme's real `settings_data.json` (228 editable settings: 53 scalar + 175 colours across 5 schemes) go to Claude → it returns a validated JSON patch (existing keys only, type-coerced) → UI shows a diff with colour swatches and per-change checkboxes → owner approves → write. Every apply snapshots the prior `settings_data.json` to `theme-backups/` for one-click **Undo**. Endpoints `/shopify/theme/{settings,suggest,apply,revert}`.
- **Blog builder** (`/ops/blog.html`) — 27 queued topics → SEO drafts for the store (publish still needs a token in Blog Studio's config.json — open item).
- **Reddit** (`/ops/reddit.html`) — a durable content queue for both own posts (`reddit_posts`) and replies (`reddit_drafts`). Queued/running work recovers after a service restart, failed work is retryable, questions can pause in `needs_input`, and health checks flag stale running/queued work. Uploaded post photos are copied into private `data/reddit-media/<post-id>/`, opened in a bounded vision-grounding pass before writing, served only through a role-checked endpoint and atomically quarantined/removed on discard. The queue is the durable in-app completion inbox; optional off-page owner alerts require `HEALTH_ALERT_TARGET`. This is the first durable job workflow, not yet the generic Runs/Inbox/Automations substrate described below.
- **System files** (`/ops/files.html`, admin-only) — a read-only source/document browser confined to `/root/ops-dashboard`, not `/root`. It excludes data, credentials, virtual environments, backups, hidden paths and symlinks, and applies the same restrictions to list/read/download. This is explicitly not Drop.
- **Order form** (`/ops/order-form.html`, added 2026-07-22) — log an order in seconds; open to any SSO user, not admin-only. Four tabs: New order / Orders / Customers / What's selling.
  - **Paste-to-fill** is the whole point: staff paste a labelled block (`Name:/Email:/Phone no:/Address:/Pincode:`) and the fields split themselves — multi-line addresses join, unlabelled blocks fall back to regex for email/phone/pincode. Parser is JS in `order_form.py` (`parseBlock`); a **Paste from clipboard** button covers phones where there's no ⌘V.
  - **Photos**: ⌘V paste event, an explicit clipboard-API button, drag-drop, or the file picker (camera roll on iOS) → uploaded via the existing `/upload`, pushed to the Drive folder "Labs OS Order Photos", links stored on the row (`photo_links` JSON, `drive_link` = first).
  - **Structure derived server-side** via `POST /orders/parse`, so the vocabulary has one home: `india_places.py` turns the address into city/state (state list + city list + "segment before the state" fallback, no pincode dataset), and `order_taxonomy.py` keyword-matches the product text into case style / dial colour / dial style / case colour / movement / size. Case-style vocabulary is seeded from the store's real `productType` values, cached in `.taxonomy-cache.json`, refreshed with `python3 order_taxonomy.py --refresh`. Colour matching is **anchored** — "rose gold blue dial" gives blue dial + rose gold case — which is the part to be careful not to regress.
  - **Customers** (`customers.py`, `customers` table) roll up from sale orders keyed on normalized 10-digit phone → email → name. SQL and Python use the same phone normalizer. Counts/spend/AOV/tags are recomputed from canonical orders rather than incremented.
  - **Editing and deletion:** supplier commitment, shipment, billing and payment boundaries lock the fields they protect. Hard delete is limited to explicit Test/Mistake/Draft pending, untouched local records; messaging-captured orders (a customer's own transcribed conversation) are permanent, full stop. A website order meeting the same untouched-pending bar instead gets **hidden** (`orders.local_hidden=1`, `POST /orders/delete` returns `hidden:true`) rather than hard-deleted: hard-deleting it would free its `shopify_order_id` and let the next sync re-insert it as a "new" order under a fresh number. The row, its items and its history all survive; `POST /orders/unhide` reverses it (the Orders-tab delete toast offers this as an inline Undo). Hidden rows are excluded everywhere an order list or total is built (`orders/list`, `supplier/orders` — moot there since hide requires `supplier_visible=0` — the Home feed, and `order_metrics.SALE_ORDER_PREDICATE`). Cancellation remains the separate, visible workflow state for anything that progressed.
  - **`shopify_build_override`**: editing `product`/`quantity` on a website order that hasn't been committed to the supplier sets this flag (mirrors the older `shopify_contact_override`, which already protected name/phone/email/address the same way). Without it, the next sync's "not committed yet, still take Shopify's word for it" rule would silently revert the correction within one timer cycle. No auto-clear — a corrected build spec has no remote value to eventually "catch up" to, unlike a contact detail.
  - **Force status reset**: `POST /orders/update` with `status` set backward on a committed build normally 409s (`{"resettable": true}` when nothing financial is attached). Re-sending with `force_status:true` bypasses the forward-only rule and records `"... (reset by staff)"` on the timeline; it still refuses outright if a shipment or bill is linked — that boundary is never bypassable from here. The supplier queue picks up a reset automatically since it reads the same `status` column live, nothing to push.
  - **Bulk build intake** is unsold stock. Every row has its own transaction and private photo copy, so a failed row cannot be accidentally committed by a later success and remains retryable.
  - **Sheet mirror** has two tabs — Orders (upsert by order number) and Customers (upsert by id in column A). Reconciliation reads each key column once and writes all explicit rows in one idempotent batch. A shared `flock` serializes every Sheet mutation across the agent service, Shopify timer and manual resync, so no process can claim a row between another's scan and write. All values use the Sheets API's `RAW` input mode so customer-supplied strings cannot become formulas. A failed batch or incompatible legacy header remains visible in health state and is retried before the Shopify watermark advances. `orders_resync.py --sheets` atomically replaces each tab's header and rows from the DB, so a reordered schema cannot place current values under legacy columns; `--backfill` separately fills DB columns on old rows. The flow only ever writes sheet-from-DB.
  - Endpoints: `POST /orders/{create,parse}`, `GET /orders/{list,meta}`, `GET /customers/list`. Inputs are **16px** — anything smaller makes iOS Safari zoom on focus and not zoom back.
  - Orders-tab column order leads with what someone scanning the list actually needs first — Product, Status, Photos — then Qty/Price/Payment/Supplier, with contact/shipping/source/logged trailing before Actions. `orders.shopify_order_id` presence (not `source`) is what the client checks to phrase a row's delete confirmation as "remove locally" vs. a real delete.

## Order lifecycle & the supplier queue (`order_stages.py`, `supplier.py`)
- **One canonical pipeline** lives in `order_stages.py` — the supplier queue, order form, sheet and server all read it. The five forward stages are **Pending → Ordered to supplier → Shipped from China → Received → Delivered**, plus `cancelled` as an off-pipeline state. `orders.status` stores the stage key; `LABELS` supplies the UI text.
- **Supplier page** (`/ops/supplier.html`) is a build queue with one tab per forward stage plus a visible Problems area for cancelled-but-still-shared records. Every channel lands in the unified order log with `supplier_visible=0`; a person explicitly sends selected orders to the supplier. Supplier responses expose specs, order number, safe event summaries and photos—not customer identity, address, internal notes, prices, ledger IDs, emails or WhatsApp targets.
- Supplier workflow is monotonic: a supplier can move exactly one step forward. Once a build is committed/assigned/shipped/billed/paid, staff cannot silently move it backward, cancel it, hide it, or change protected specs (staff have the explicit force-reset override above; suppliers do not). Bill lines store quantity and currency; mixed-currency bills are rejected and reporting converts each bill individually. `orders.notes` (staff's own sizing/deadline shorthand) is included in the supplier feed as of 2026-07-30 — a deliberate reversal of the earlier withhold-it-by-default call, since it's useful to whoever is actually building the watch; it can still incidentally carry a stray customer detail if someone pastes carelessly.
- **Draft bills are editable past price**: `POST /supplier/bill/update` also accepts `add_ids`/`remove_order_ids` to change which orders are on a batch, not just re-price its existing lines — same draft-and-unpaid-only envelope as everything else in that handler, same "at least one item" floor a batch already implied. A removed order returns to the unbilled queue; an added one is priced the same way batch-creation prices an unpriced build (its own `supplier_cost`, or the movement default). The supplier page's edit-bill sheet is a real small form now, not a chain of `prompt()`s.
- **Migration is one-shot, gated on `PRAGMA user_version`** (not value-based), because old "shipped" (to customer = done) had to become "delivered" while "shipped" is *also* a new key — a value guard can't tell them apart. `user_version=1` means it's done. Bumping the pipeline again needs a new version + one-shot block, not a value CASE.
- **`orders.order_no`** is the human-facing number (`#61`), kept separate from `orders.id` (which photos, the sheet join and Shopify links key off, so it can't be renumbered). Existing rows were seeded to their id; `order_number_seq` allocates each new number transactionally in create/bulk/Shopify-sync and never reuses one after a hard delete. A stage change best-effort-syncs the sheet's Status cell (`google_api.update_order_field`).
- **Canonical sales predicate** lives in `order_metrics.py`: exclude `status='cancelled'`, refunded/voided financial states and `is_stock=1`. Use it everywhere revenue/order/customer performance is calculated; do not invent a page-local variant.

## Google (Drive + Sheets)
`google_api.py` is the shared access layer for both — stdlib `urllib` only (no `gspread`), so system python can import it. Client at `/root/oauth-client.json`, token at `.gdrive-token.json`, IDs cached in `.orders-sheet.json` (all gitignored).
- `google_token_store.py` is the one token reader/refresher for every process. Refreshes take a cross-process file lock and replace the token atomically with mode 0600, preventing concurrent services from truncating or racing the credential.
- **Live token holds only `drive.file` + `drive.readonly` — and that is sufficient for Sheets**, because `drive.file` covers any file the app itself created and Labs OS created the Orders spreadsheet. Enabling the Sheets API in the Google Cloud project was the only thing needed; **no reconnect was required.**
- `/gdrive/connect` now also requests `spreadsheets`, which only matters if you ever want to write to a spreadsheet a human created by hand — `drive.file` cannot touch those. That wider scope applies automatically the next time Google is reconnected for any reason.


## Driving it from a terminal (and how Hermes acts)
`labs` (/usr/local/bin/labs -> bin/labs) exposes the whole system to the shell and therefore to the agent. It imports the same shopify_api.py / google_api.py the web tools use, so it reuses the credentials already in .env — never issue new Shopify/Google keys.
- Reads: `labs orders` (live storefront + logged, merged), `products`, `product <id>`, `pages`, `page <id>`, `blogs`, `articles`, `article <id>`, `theme [--filter]`, `costs`, `drive`, `search "green dial"` (Drop photos by content), `files`, `customers`, `events`, `access`, `topics`.
- Writes: `product-create/update`, `page-update`, `article-create/update`, `theme-set key=value`. **Every write is a dry run that prints the plan until you add `--execute`**, and executed writes log to `hub_events`.
- **Agent toolset is role-aware**: admins get `terminal` (so the agent can actually run `labs`), everyone else keeps the safe web-only set. `/send` is reachable by any signed-in user, so a blanket grant would let a restricted role run root commands; admins already hold root SSH so it adds no privilege for them. See `toolset_for()` in agent_chat_server.py.
- `memory_facts` now also carries categories **`preference`** (how the owner wants work done, the writing voice, design taste, what is ruled out, safety rules) and **`business`** (price bands, landed cost, banking overhead, order channels). Read those before writing copy or building UI.

## Backup, deploy and operating discipline
- Treat this checkout as production. Before migrations or deploys, run `backup.py`, confirm both local and offsite success, inspect the archive inventory and run SQLite integrity checks. The backup takes one cross-database snapshot of `hermes.db` and `suppliers.db`, verifies supplier-bill ↔ Ledger links in both directions, and requires the archived Reddit-media manifest to match the database exactly. It remains unencrypted and deliberately excludes the multi-gigabyte Drop library, so it is not yet the complete DR package described above.
- Validate changed Python with AST, regenerate all affected pages, extract every emitted `<script>` and run `node --check`, then run the venv `healthcheck.py`.
- Install generated output only through generators. Test nginx with `nginx -t` before reload. Restart changed services, probe role boundaries and public/private routes, test desktop/tablet/mobile, review logs/services/timers, and inspect `git diff --check`, `git diff` and `git status`.
- Commit the reviewed production state on `order-form` with the problem/cause/fix in the message. Do not merge to `main` until the owner declares order work complete.
- Shopify writes and destructive data reconciliation need a reviewed dry run or explicit owner approval. New orders always start supplier-hidden.
